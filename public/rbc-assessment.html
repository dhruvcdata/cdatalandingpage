Design Decisions — Why This Schema

Why 2 Fact Tables (not 1, not 4)?

FACT 1 Premium — Money Flows IN

Grain: 1 row per premium transaction

Measure: premium_change_amount (+ve new/renewal, -ve cancel)

Every dollar traceable for SOX audit.

FACT 2 Claims — Money Flows OUT

Grain: 1 row per claim payment or status change

Measures: claim_amount, paid_amount, outstanding

Full lifecycle: report → reserve → pay → close.

Why not 1 combined table? Different grains — a premium transaction is a fundamentally different event from a claim payment. Combining forces NULLs everywhere and makes queries confusing. Why not 4? Claims + Claim Payments merge into one event-level fact (same grain: claim lifecycle events).

Why SCD Type 2 on dim_policy?

Policies change mid-term (endorsements). Actuarial needs to know what the policy looked like when a claim happened.

Endorsement: teen driver added on Mar 1
Version 1 (Expired)
policy_key = 101
Coverage: $50K  |  Premium: $1,200
valid_from: Jan 1 → valid_to: Feb 28
is_current: FALSE
Version 2 (Current)
policy_key = 102
Coverage: $75K  |  Premium: $1,800
valid_from: Mar 1 → valid_to: 9999-12-31
is_current: TRUE

Claim in April → joins to policy_key 102 (version active at loss date) → accurate loss ratio

Why a Pre-Computed Aggregate?

agg_monthly_financial

  • Finance queries the monthly close report hundreds of times during close week
  • Fact table scan = minutes. Aggregate = seconds.
  • Includes earned premium (pro-rata daily), loss ratio, reserve changes

Key Rule

Aggregate is a cache, not a source of truth.

ETL validates: SUM(fact) = SUM(agg) per product line per month. Mismatch > $0.01 → batch fails.

Earned Premium: 12-month policy, $1,200, effective Jan 1 → Feb earned = $1,200 / 12 = $100. Policy starting Feb 15 → earns 14/28 of monthly rate = $50.

DDL — fact_premium_transaction

CREATE TABLE insurance_mart.fact_premium_transaction (
    -- Surrogate key
    transaction_key       BIGINT        IDENTITY(1,1)  PRIMARY KEY,

    -- Dimension foreign keys
    date_key              INT           NOT NULL       REFERENCES insurance_mart.dim_date(date_key),
    policy_key            BIGINT        NOT NULL       REFERENCES insurance_mart.dim_policy(policy_key),
    geo_key               INT           NOT NULL       REFERENCES insurance_mart.dim_geography(geo_key),

    -- Degenerate dimensions (audit trail)
    transaction_id        VARCHAR(50)   NOT NULL,       -- Source system PK
    policy_id             VARCHAR(50)   NOT NULL,       -- Natural key for reconciliation
    transaction_date      DATE          NOT NULL,

    -- Transaction attributes
    transaction_type      VARCHAR(20)   NOT NULL,       -- New Business, Renewal, Endorsement, Cancellation
    reason_code           VARCHAR(20),

    -- Measures (additive)
    premium_change_amount NUMERIC(15,2) NOT NULL,       -- +ve for new/renewal, -ve for cancel

    -- ETL metadata
    etl_batch_id          BIGINT        NOT NULL,
    etl_loaded_at         TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP(),
    source_system         VARCHAR(30)   DEFAULT 'POLICY_ADMIN'
)
CLUSTER BY (transaction_date, transaction_type);

ALTER TABLE insurance_mart.fact_premium_transaction
  ADD CONSTRAINT uq_fact_premium_txn UNIQUE (transaction_id);

Design Decisions

  • NUMERIC(15,2) — avoids floating-point rounding in financial data
  • Degenerate dimensions (transaction_id, policy_id) — audit trail without extra joins
  • Cluster key on date + type — aligns with month-end queries

Idempotency & Audit

  • etl_batch_id — traces every row to a specific load
  • Unique constraint on transaction_id prevents duplicate loads
  • source_system — supports multi-source reconciliation

DDL — dim_policy (SCD Type 2)

CREATE TABLE insurance_mart.dim_policy (
    -- Surrogate key (new row per version)
    policy_key            BIGINT        IDENTITY(1,1)  PRIMARY KEY,

    -- Natural key
    policy_id             VARCHAR(50)   NOT NULL,
    policy_number         VARCHAR(30)   NOT NULL,

    -- Policy attributes
    customer_id           VARCHAR(50)   NOT NULL,
    agent_id              VARCHAR(50),
    product_line          VARCHAR(20)   NOT NULL,       -- Auto, Home, Commercial, Life
    coverage_type         VARCHAR(30)   NOT NULL,
    coverage_amount       NUMERIC(15,2) NOT NULL,
    effective_date        DATE          NOT NULL,
    expiry_date           DATE          NOT NULL,
    premium_amount        NUMERIC(15,2) NOT NULL,
    policy_term_months    INT           NOT NULL,
    policy_status         VARCHAR(20)   NOT NULL,
    state_code            VARCHAR(5),
    region                VARCHAR(30),

    -- Derived: monthly earned premium rate (populated by ETL)
    monthly_earned_rate   NUMERIC(15,2) NOT NULL,       -- premium_amount / policy_term_months

    -- SCD Type 2 tracking
    valid_from            TIMESTAMP_NTZ NOT NULL,
    valid_to              TIMESTAMP_NTZ DEFAULT '9999-12-31'::TIMESTAMP_NTZ,
    is_current            BOOLEAN       DEFAULT TRUE,

    -- ETL metadata
    etl_batch_id          BIGINT        NOT NULL,
    etl_loaded_at         TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP(),
    row_hash              VARCHAR(64)   NOT NULL        -- SHA-256 for change detection
)
CLUSTER BY (product_line, is_current);

-- Note: Snowflake uses clustering keys instead of indexes.
-- Filter on is_current = TRUE for current-state queries.
Why SCD2: Endorsements change coverage mid-term. Old row → is_current=FALSE, new row created. This lets actuarial report on what the policy looked like when a claim occurred. The row_hash enables efficient change detection in ETL.

Query 1 — Premium Activity by Product Line (Feb 2026)

WITH premium_activity AS (
    SELECT
        p.product_line,
        f.transaction_type,
        SUM(f.premium_change_amount)  AS total_premium
    FROM insurance_mart.fact_premium_transaction  f
    JOIN insurance_mart.dim_policy               p  ON f.policy_key = p.policy_key
    JOIN insurance_mart.dim_date                 d  ON f.date_key   = d.date_key
    WHERE d.calendar_year  = 2026
      AND d.calendar_month = 2
    GROUP BY p.product_line, f.transaction_type
)
SELECT
    product_line,
    SUM(CASE WHEN transaction_type = 'New Business'  THEN total_premium ELSE 0 END)  AS new_business_premium,
    SUM(CASE WHEN transaction_type = 'Renewal'       THEN total_premium ELSE 0 END)  AS renewal_premium,
    SUM(CASE WHEN transaction_type = 'Endorsement'   THEN total_premium ELSE 0 END)  AS endorsement_changes,
    SUM(CASE WHEN transaction_type = 'Cancellation'  THEN total_premium ELSE 0 END)  AS cancellation_returns,
    SUM(total_premium)  AS net_written_premium
FROM premium_activity
GROUP BY product_line
ORDER BY product_line;
Note: Cancellations are negative by convention. net_written_premium is the algebraic sum — reconciles directly with general ledger.

Query 2 — Earned Premium by Product Line (Feb 2026)

-- Earned premium = pro-rata portion of written premium recognized in February

SELECT
    p.product_line,
    COUNT(DISTINCT p.policy_id)       AS active_policies,
    SUM(
        p.premium_amount / p.policy_term_months
        * GREATEST(
            DATEDIFF('day',
                GREATEST(p.effective_date,  '2026-02-01'::DATE),
                LEAST(p.expiry_date,    '2026-02-28'::DATE) + 1
            ), 0
        )
        / 28.0
    )                                     AS earned_premium
FROM insurance_mart.dim_policy p
WHERE p.is_current = TRUE
  AND p.policy_status IN ('Active', 'Cancelled')
  AND p.effective_date <= '2026-02-28'::DATE
  AND p.expiry_date    >= '2026-02-01'::DATE
GROUP BY p.product_line
ORDER BY p.product_line;

Query 3 — Claims Activity & Combined Close (Feb 2026)

WITH new_claims AS (
    SELECT p.product_line,
           COUNT(DISTINCT c.claim_id) AS new_claims_count,
           SUM(c.claim_amount)          AS new_claims_incurred
    FROM insurance_mart.fact_claim_activity c
    JOIN insurance_mart.dim_policy p ON c.policy_key = p.policy_key
    JOIN insurance_mart.dim_date   d ON c.report_date_key = d.date_key
    WHERE d.calendar_year = 2026 AND d.calendar_month = 2
    GROUP BY p.product_line
),
claims_paid AS (
    SELECT p.product_line, SUM(c.paid_amount) AS feb_paid
    FROM insurance_mart.fact_claim_activity c
    JOIN insurance_mart.dim_policy p ON c.policy_key = p.policy_key
    JOIN insurance_mart.dim_date   d ON c.date_key   = d.date_key
    WHERE d.calendar_year = 2026 AND d.calendar_month = 2
    GROUP BY p.product_line
),
reserves AS (
    -- Reserve change already pre-computed in the monthly aggregate
    SELECT product_line,
           SUM(reserves_change) AS reserve_change
    FROM insurance_mart.agg_monthly_financial
    WHERE month_key = (SELECT date_key FROM insurance_mart.dim_date
                      WHERE full_date = '2026-02-28'::DATE)
    GROUP BY product_line
)
SELECT
    COALESCE(nc.product_line, cp.product_line, r.product_line) AS product_line,
    nc.new_claims_count, nc.new_claims_incurred,
    cp.feb_paid            AS claims_paid_in_feb,
    r.reserve_change       AS reserve_change_jan_to_feb,
    cp.feb_paid + r.reserve_change  AS total_incurred
FROM new_claims nc
FULL OUTER JOIN claims_paid cp ON nc.product_line = cp.product_line
FULL OUTER JOIN reserves     r  ON nc.product_line = r.product_line
ORDER BY product_line;

Critical Design Trade-offs & Data Quality

Q1: Transaction Detail vs. Monthly Aggregates

Dual-Layer Approach

  • Transaction-level facts preserve every event for audit, SOX compliance, ad-hoc analysis
  • Pre-computed aggregate serves dashboards and monthly close — seconds vs minutes
  • Reconciliation: ETL asserts SUM(fact) = SUM(agg) per product line per month. Mismatch > $0.01 fails the batch
  • Snowflake clustering on transaction_date gives aggregate-like performance on facts when needed
Key principle: Aggregates are a performance optimization, not a source of truth. Fact tables are always authoritative.

Q2: Anticipated Data Quality Issue

Late-Reported Claims (IBNR)

  • Issue: loss_date may precede report_date by weeks/months. Auto accident in Jan reported in Mar.
  • Impact: Feb close understates incurred claims for Feb losses. Distorts loss ratios.

Detection & Mitigation

  • Detection: Monitor DATEDIFF(loss_date, report_date) distribution. Alert if avg lag exceeds norms
  • Model: fact_claim_activity carries both loss_date_key and report_date_key for accident-period vs report-period analysis
  • Fix: IBNR reserve estimate in aggregate (computed by actuarial models outside this mart)

dbt Best Practices

  • Staging: 1:1 with source, rename + type-cast
  • Intermediate: SCD2, dedup
  • Mart: Star schema tables
  • Tests: unique, not_null, relationships + balance checks

Monthly Close Process

  • Day 1-2: ETL loads through month-end
  • Day 3: Reconciliation: fact vs aggregate
  • Day 4: Finance reviews, signs off
  • Day 5: Regulatory reports, month locked

SOX Compliance Controls

  • Immutable facts: No UPDATE — corrections via reversing entries
  • Audit trail: Every row tagged with batch_id + timestamp
  • Month lock: Aggregate frozen after close
